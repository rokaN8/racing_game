# IndexedDB for Ghost storage: research

Research for [#73](https://github.com/rokaN8/racing_game/issues/73), feeding [#74](https://github.com/rokaN8/racing_game/issues/74) (Ghost storage on IndexedDB). It records facts only; the design decision belongs to #74. Sources were read on 2026-11-28. Engine source links are pinned to the commit that was read: Chromium `87d4173f`, WebKit `6d626a42`, Firefox `ac1fc475`.

**Today** (`src/ghost.ts`, `docs/game-spec.md` → Storage): 5 Tracks × 3 lap counts = 15 localStorage keys (`neon-racer.track.<id>.v1`, `.<n>laps.v1`), plus the two pre-Track keys `neon-racer.ghost.v2` / `.v1` that `migrateOldGhost` moves into Overdrive. Each key is one JSON record. The Ghost's poses (7 floats per physics step at 120 Hz) and run distances are base64 Float32Arrays. Every storage call is in a try/catch, and when a write fails the Ghost lives in memory only. `main.ts` creates every Ghost synchronously at boot and reads `ghost().bestTime` straight away. The map issue puts the worst case at ~10.8 MB of base64, which is over the localStorage quota.

## 1. Blocked storage and private browsing

### What the specs say

- **`indexedDB.open()` throws synchronously when storage is unavailable.** The open steps are: a version of 0 throws `TypeError`; then *obtain a storage key*, and "if failure is returned, then throw a "SecurityError" DOMException" ([IndexedDB 3.0 → `open()`](https://w3c.github.io/IndexedDB/#dom-idbfactory-open)). Obtaining a storage key fails when "key's origin is an opaque origin" or "if the user has disabled storage" ([Storage Standard → obtain a storage key](https://storage.spec.whatwg.org/#obtain-a-storage-key)).
- **Everything after that is asynchronous.** "The API methods return without blocking the calling thread" ([IndexedDB → async API](https://w3c.github.io/IndexedDB/#async-api)). The spec has no synchronous API. Opening a connection can still fail later, as an `error` event on the request: `VersionError` for a lower version, `AbortError` if the connection closes during an upgrade, and creating the database can fail "for any reason" with "an appropriate error (e.g. a QuotaExceededError, or an "UnknownError" DOMException)" ([IndexedDB → opening a database connection](https://w3c.github.io/IndexedDB/#opening)).
- **An open can wait.** If another connection (another tab) stays open after its `versionchange` event, the request gets `blocked` and waits for it to close ([IndexedDB → handling versionchange](https://w3c.github.io/IndexedDB/#handling-versionchange)). MDN advises closing the database in `onversionchange`: "If you don't do this then the upgrade won't happen until the user closes the tab" ([MDN → Using IndexedDB](https://developer.mozilla.org/en-US/docs/Web/API/IndexedDB_API/Using_IndexedDB)).
- **localStorage behaves the same way.** Its getter throws `SecurityError` "if the request violates a policy decision (e.g., if the user agent is configured to not allow the page to persist data)", and `setItem` throws `QuotaExceededError` ([HTML → Web storage](https://html.spec.whatwg.org/multipage/webstorage.html#the-localstorage-attribute)).

### What each browser does

| | Storage blocked for the site | Private window |
|---|---|---|
| **Chrome** (Blink) | `open()` returns a request, which then fires `error` asynchronously with `UnknownError` "The user denied permission to access the database." An opaque origin throws `SecurityError` synchronously instead. | Works, in memory. Thrown away at the end of the session. |
| **Firefox** (Gecko) | Firefox 127 and later: `open()` throws `SecurityError` "The operation is insecure" synchronously. Before 127, just reading `window.indexedDB` threw. | Firefox 115 and later: works, encrypted on disk, purged at the end of the session. Before 115: failed with `InvalidStateError`. |
| **Safari** (WebKit; every iOS browser) | `open()` throws `SecurityError` synchronously when the storage blocking policy is "block all", or for opaque and `file:` origins. | Works, with an in-memory backing store. Blob values have failed there in the past. |

Details and sources:

- **Chrome.** `IDBFactory::OpenInternal` throws `SecurityError` ("access to the Indexed Database API is denied in this context.") only when the origin `!CanAccessDatabase()`, that is, an opaque origin. When the content settings deny storage (the user blocked site data, or a third-party context with third-party cookies blocked), `OpenInternalImpl` calls `OnDBFactoryError` with `kUnknownError` / `kPermissionDeniedErrorMessage`. The code posts this as a task on purpose because "As per IDB spec, firing the event at the request has to be asynchronous" ([`idb_factory.cc`](https://chromium.googlesource.com/chromium/src/+/87d4173ffc4777681fce89a36e351fc45c5964a6/third_party/blink/renderer/modules/indexeddb/idb_factory.cc)). Reading the `indexedDB` getter does not throw. Under the same settings the localStorage getter throws `SecurityError` "Access is denied for this document" ([`dom_window_storage.cc`](https://chromium.googlesource.com/chromium/src/+/87d4173ffc4777681fce89a36e351fc45c5964a6/third_party/blink/renderer/modules/storage/dom_window_storage.cc), [chromium.org note](https://www.chromium.org/for-testers/bug-reporting-guidelines/uncaught-securityerror-failed-to-read-the-localstorage-property-from-window-access-is-denied-for-this-document/)).
  - Incognito: the IndexedDB context is `in_memory()` when the profile has no data path ([`indexed_db_context_impl.h`](https://chromium.googlesource.com/chromium/src/+/87d4173ffc4777681fce89a36e351fc45c5964a6/content/browser/indexed_db/indexed_db_context_impl.h)). The quota is computed from RAM (see §2).
- **Firefox.** When `StorageAllowedForWindow` is `eDeny` (cookies blocked for the site), the factory is created with `mAllowed = false`, and `Open()` / `DeleteDatabase()` / `databases()` throw or reject with `SecurityError` "The operation is insecure" ([`IDBFactory.cpp`](https://github.com/mozilla-firefox/firefox/blob/ac1fc4756876469bc1ea6f7e610c3c240cb14a26/dom/indexedDB/IDBFactory.cpp#L422-L432): `kAccessError` L58, `AllowedForWindowInternal` L272-L300, `Open` L422-L432). This behaviour came with Firefox 127 ([bug 1878137](https://bugzilla.mozilla.org/show_bug.cgi?id=1878137), "Defer reporting declined IDB storage access to method calls").
  - Before 127, `typeof indexedDB` itself threw "SecurityError: The operation is insecure." when cookies were disabled ([bug 1287440](https://bugzilla.mozilla.org/show_bug.cgi?id=1287440)). MDN's storage access policy page still says that "attempting to access the IndexedDB factory object throws a `SecurityError`", and that localStorage "read and write attempts throw a `SecurityError`" ([MDN → Storage access policy](https://developer.mozilla.org/en-US/docs/Web/Privacy/Guides/Storage_Access_Policy)).
  - Private browsing: "IndexedDB is now also supported in private browsing without memory limits thanks to encrypted storage on disk… all stored information is purged at the normal end of a private browsing session" ([Firefox 115 release notes](https://www.firefox.com/en-US/firefox/115.0/releasenotes/), [bug 1639542](https://bugzilla.mozilla.org/show_bug.cgi?id=1639542)). Before 115, opening failed in private windows. Reporters saw an `InvalidStateError` on `onerror`, and some saw an uncatchable throw ([bug 781982](https://bugzilla.mozilla.org/show_bug.cgi?id=781982), comments 27 and 31).
- **Safari / WebKit.** `IDBFactory::openInternal` returns `SecurityError` "IDBFactory.open() called in an invalid security context" when `canAccessResource(IndexedDB)` is `No`, or when the document has no frame or page ([`IDBFactory.cpp` L50-L101](https://github.com/WebKit/WebKit/blob/6d626a42f354af9e4169fd2ee062de075b79568a/Source/WebCore/Modules/indexeddb/IDBFactory.cpp#L50-L101)). `canAccessResource` returns `No` for opaque origins, for `file:`-like origins, and when `StorageBlockingPolicy::BlockAll` is set. IndexedDB and LocalStorage are in the same case group there. Under `BlockThirdParty`, a third-party frame gets a *transient* database ([`ScriptExecutionContext::canAccessResource`](https://github.com/WebKit/WebKit/blob/6d626a42f354af9e4169fd2ee062de075b79568a/Source/WebCore/dom/ScriptExecutionContext.cpp)). *Not verified:* which Safari setting maps to `BlockAll`. Safari's UI code is not public; "Block All Cookies" is the likely one.
  - Private Browsing: `IDBStorageManager::createBackingStore` uses a `MemoryIDBBackingStore` (or a SQLite in-memory store) when the storage path is empty or the database is transient. WebKit treats an empty path as the ephemeral session ("No need to perform eviction for ephemeral session") ([`IDBStorageManager.cpp`](https://github.com/WebKit/WebKit/blob/6d626a42f354af9e4169fd2ee062de075b79568a/Source/WebKit/NetworkProcess/storage/IDBStorageManager.cpp), [`NetworkStorageManager.cpp` L633-L640](https://github.com/WebKit/WebKit/blob/6d626a42f354af9e4169fd2ee062de075b79568a/Source/WebKit/NetworkProcess/storage/NetworkStorageManager.cpp#L633-L640)). Private mode has rejected **Blob** values before: "BlobURLs are not yet supported" on iOS 12 ([WebKit 198278](https://bugs.webkit.org/show_bug.cgi?id=198278)), and "Error preparing Blob/File data" in Safari 17 ([WebKit 268037](https://bugs.webkit.org/show_bug.cgi?id=268037)). Typed arrays and ArrayBuffers are not Blobs.
  - Historical: on Safari 14.1.1 / iOS 14.6 the first `indexedDB.open()` could stay `pending` forever with no events fired. The fix shipped in iOS 14.7 ([WebKit 226547](https://bugs.webkit.org/show_bug.cgi?id=226547)). It shows that an open request is not guaranteed to settle.
  - iOS: "Apps that browse the web must use the appropriate WebKit framework" unless they hold the EU/Japan alternative-engine entitlement ([App Review Guideline 2.5.6](https://developer.apple.com/app-store/review/guidelines/#2.5.6)). Chrome and Firefox on iOS therefore behave like Safari.
- **Not a browser.** Node has no `indexedDB` global: `typeof indexedDB === 'undefined'` on Node 24.6, checked locally. Browser compat data lists Deno as `false` ([BCD `api/_globals/indexedDB.json`](https://github.com/mdn/browser-compat-data/blob/main/api/_globals/indexedDB.json)).

### The failure shapes a guard has to cover

1. Reading `indexedDB` throws (Firefox before 127 with cookies blocked).
2. `indexedDB` is undefined (Node, other non-browser runtimes).
3. `open()` throws `SecurityError` synchronously (the spec, Firefox 127+, WebKit, Chrome for opaque origins).
4. `open()` fires `error` asynchronously (Chrome when the user blocked storage, `VersionError`, Firefox private windows before 115).
5. `open()` never settles: `blocked` behind another tab's open connection, or the historical WebKit hang.
6. Storage works but in memory only (Chrome Incognito, Safari Private) or is purged at the end of the session (Firefox private). localStorage behaves the same way in all three.
7. The write fails later: the transaction aborts at commit with `QuotaExceededError` or `UnknownError` (§2).

## 2. Quota and eviction for the GitHub Pages origin

- **The origin is shared.** A project site is served at `http(s)://<owner>.github.io/<repositoryname>` ([GitHub Docs → About GitHub Pages](https://docs.github.com/en/pages/getting-started-with-github-pages/about-github-pages)). The path is not part of the origin, so every project site of the owner shares `https://rokan8.github.io`: one localStorage, one IndexedDB namespace and one quota. `github.io` is on the [Public Suffix List](https://publicsuffix.org/list/public_suffix_list.dat), so the site (eTLD+1) is `rokan8.github.io` itself. That matters for Firefox's group limit and Chrome's `persist()` heuristics below.
- **localStorage quota.** The Storage Standard gives the `localStorage` endpoint a quota of 5 × 2²⁰ bytes; `indexedDB` and `caches` have none of their own (null), only the shelf's ([Storage Standard → registered endpoints](https://storage.spec.whatwg.org/#registered-storage-endpoints)). MDN: "Browsers can store up to 5 MiB of local storage… per origin", and going over throws `QuotaExceededError` ([MDN → Storage quotas](https://developer.mozilla.org/en-US/docs/Web/API/Storage_API/Storage_quotas_and_eviction_criteria)). Chrome's area quota is `kPerStorageAreaQuota = 10485760` bytes, and "For quota purposes we count each character as 2 bytes". That is ~5.2 M characters ([`storage_area.mojom`](https://chromium.googlesource.com/chromium/src/+/87d4173ffc4777681fce89a36e351fc45c5964a6/third_party/blink/public/mojom/dom_storage/storage_area.mojom), [`storage_area_map.cc`](https://chromium.googlesource.com/chromium/src/+/87d4173ffc4777681fce89a36e351fc45c5964a6/third_party/blink/renderer/modules/storage/storage_area_map.cc)).
- **IndexedDB quota per origin** ([MDN → Storage quotas](https://developer.mozilla.org/en-US/docs/Web/API/Storage_API/Storage_quotas_and_eviction_criteria) unless noted):
  - **Chrome:** up to 60 % of total disk, the same in best-effort and persistent mode. The source has a pool of 80 % of disk (`PoolSizeRatio`), of which each storage key gets 75 % ([`quota_settings.cc`](https://chromium.googlesource.com/chromium/src/+/87d4173ffc4777681fce89a36e351fc45c5964a6/storage/browser/quota/quota_settings.cc), [`quota_features.cc`](https://chromium.googlesource.com/chromium/src/+/87d4173ffc4777681fce89a36e351fc45c5964a6/storage/browser/quota/quota_features.cc)). **Incognito:** a pool of 15–20 % of *physical memory* (random within that range), and each origin gets a third of the pool (`CalculateIncognitoDynamicSettings`).
  - **Firefox:** best-effort is the smaller of 10 % of disk and a 10 GiB group limit shared by all origins of the same site. Persistent is up to 50 % of disk, capped at 8 TiB, with no group limit.
  - **Safari 17+ (macOS 14, iOS 17):** browser apps get up to ~60 % of disk per origin, other WebKit apps ~15 %. All origins together are capped at 80 % (browser) or 20 % (other apps). Home Screen / Dock web apps get the browser's quotas. Cross-origin frames get 1/10. Safari no longer prompts for more space ([WebKit → Updates to Storage Policy](https://webkit.org/blog/14403/updates-to-storage-policy/)). Earlier Safari versions gave 1 GiB, then asked the user.
- **What that means for Ghost sizes.** Raw Float32 bytes are 3/4 of the base64 character count. The ~10.8 MB base64 worst case is about **8.1 MB raw**, which is far inside every quota above. The tightest is Chrome Incognito: a 4 GiB device gets a 0.6–0.8 GiB pool, so about 200–270 MiB per origin. In Chrome's localStorage the same base64 costs 2 bytes per character (~21.6 MB against 10 MiB).
- **Eviction.** Storage is best-effort unless it is made persistent. Under storage pressure the user agent "should clear… local storage buckets whose mode is "best-effort"", and a cleared bucket "must be cleared in its entirety" ([Storage Standard → storage pressure](https://storage.spec.whatwg.org/#storage-pressure), [management](https://storage.spec.whatwg.org/#management)). localStorage and IndexedDB are endpoints of the same local bucket, so **they are evicted together**. Browsers pick the least recently used origin first. Chrome starts evicting when all data passes 80 % of disk. Persistent origins are skipped ([MDN](https://developer.mozilla.org/en-US/docs/Web/API/Storage_API/Storage_quotas_and_eviction_criteria)).
  - **Safari also evicts on its own schedule.** Since Safari 13.1 / iOS 13.4, ITP deletes "all of a website's script-writable storage after seven days of Safari use without user interaction on the site". That covers IndexedDB and LocalStorage alike. Home Screen web apps "have their own counter of days of use" ([WebKit → Full Third-Party Cookie Blocking and More](https://webkit.org/blog/10218/full-third-party-cookie-blocking-and-more/)). WebKit's time-based and quota-based eviction skip origins that are active or persisted (`performTimeBasedEviction`, `performQuotaBasedEviction` in [`NetworkStorageManager.cpp`](https://github.com/WebKit/WebKit/blob/6d626a42f354af9e4169fd2ee062de075b79568a/Source/WebKit/NetworkProcess/storage/NetworkStorageManager.cpp)). Moving from localStorage to IndexedDB does not change any of this.
- **`navigator.storage.persist()`** asks for the `"persistent-storage"` permission ([Storage Standard → persistence](https://storage.spec.whatwg.org/#persistence)).
  - **Chrome** never prompts. It grants only to a top-level origin. It refuses when cookies are session-only or blocked. It grants when the registrable domain is an installed app or one of the top 10 "important sites" by engagement; otherwise it returns false ([`persistent_storage_permission_context.cc`](https://chromium.googlesource.com/chromium/src/+/87d4173ffc4777681fce89a36e351fc45c5964a6/chrome/browser/storage/persistent_storage_permission_context.cc)).
  - **Firefox** shows the user a permission popup.
  - **Safari** (15.2+) decides "based on the user's history of interaction with the site", with no prompt ([MDN](https://developer.mozilla.org/en-US/docs/Web/API/Storage_API/Storage_quotas_and_eviction_criteria)). WebKit's example heuristic is "whether the site is opened as a Home Screen Web App" ([WebKit blog](https://webkit.org/blog/14403/updates-to-storage-policy/)). In the source, `persistOrigin` grants only to domains the app reports as exempt from website-data deletion, and a private session always gets `false` ([`NetworkStorageManager::persist`](https://github.com/WebKit/WebKit/blob/6d626a42f354af9e4169fd2ee062de075b79568a/Source/WebKit/NetworkProcess/storage/NetworkStorageManager.cpp#L942-L962)).
  - Support: `persist`/`persisted` in Chrome 55, Firefox 57 and Safari 15.2. `estimate` in Chrome 61, Firefox 57 and Safari 17 ([BCD `api/StorageManager.json`](https://github.com/mdn/browser-compat-data/blob/main/api/StorageManager.json)). `estimate()` returns an estimate, padded for cross-origin data.
- **Quota errors in IndexedDB.** "If an error occurs while writing the changes to the database, then run abort a transaction", for example with a QuotaExceededError ([IndexedDB → commit a transaction](https://w3c.github.io/IndexedDB/#commit-transaction)). The failure therefore shows up as the transaction's `abort` event with `transaction.error` set. It can arrive even after every `put` request has reported success.
- **Durability.** Since Chrome 121, `readwrite` transactions default to `relaxed` durability, "to align with other major browsers like Firefox and Safari". With relaxed, "the data is still in the process of being written when the complete event fires". `{ durability: 'strict' }` is still available ([Chrome blog](https://developer.chrome.com/blog/indexeddb-durability-mode-now-defaults-to-relaxed), [MDN → durability](https://developer.mozilla.org/en-US/docs/Web/API/IDBTransaction/durability)).

## 3. Migrating the existing localStorage keys

The repo already has a migration pattern: `migrateOldGhost` writes the new record and removes the old keys only once that write succeeds (`docs/game-spec.md` → Storage → Migration). These facts bear on doing the same from localStorage to IndexedDB:

- **When the write has landed.** The localStorage read is synchronous; the IndexedDB write is not. Success is the transaction's `complete` event, which "is fired at a transaction that has successfully committed" ([IndexedDB → transaction lifecycle](https://w3c.github.io/IndexedDB/#transaction-lifecycle)). A `put` request's `success` comes before the commit, and the commit can still abort (§2). Under the default relaxed durability, `complete` means the data has gone to the OS, not necessarily to disk.
- **The two stores have no shared transaction.** If the page closes between `complete` and `removeItem`, both copies remain, so a migration that runs on every boot has to tolerate finding its own earlier result.
- **Several tabs can migrate at once.** Read/write transactions with overlapping scopes run one after another: one "can start when there are no transactions which: were created before tx; and have overlapping scopes with tx; and are not finished" ([IndexedDB → transaction scheduling](https://w3c.github.io/IndexedDB/#transaction-scheduling)). Two tabs migrating the same key therefore serialize; the second write overwrites the first.
- **Keeping the old keys protects nothing from eviction.** They are evicted and cleared together with IndexedDB (same bucket, §2). They keep counting against localStorage's ~5 MiB and the origin's usage.
- **Keeping them rarely helps when IndexedDB is unavailable.** The same settings that block IndexedDB also block localStorage in all three engines: Chrome's `CanAccessStorage`, Firefox's `eDeny` / storage access policy ("localStorage also returns SECURITY_ERR", [bug 1287440 c8](https://bugzilla.mozilla.org/show_bug.cgi?id=1287440)), and WebKit's shared `canAccessResource` case. In current private modes both work, and both go away at the end of the session.
- **Kept keys interact with Reset.** Reset is `removeItem` on the Track's keys today (`docs/game-spec.md` → Storage → Reset). Suppose the old keys stay and the migration copies them whenever IndexedDB has no record. Then a Reset that only deletes from IndexedDB would bring the old High scores back on the next boot.
- **What the old data holds.** The old poses are base64 strings that `decode()` already turns into a validated `Float32Array`, rejecting non-finite values and lengths that aren't whole records. A migrated record could hold the decoded arrays directly (§5). Keys from before lap counts (1-Lap records without `lapTimes`) and records without `dist` or `sectors` already load through `load()`'s fallbacks.

## 4. Testing under vitest in Node

- **The setup.** Vitest's default `environment` is `'node'` ([Vitest → environment](https://vitest.dev/config/environment)), and Node has no IndexedDB (§1). `setupFiles` "will run before each test file in the same process" ([Vitest → setupFiles](https://vitest.dev/config/setupfiles)). The current tests inject `Storage`-shaped fakes into `createGhost`: `memoryStorage()`, a `blocked` Proxy that throws on every access, and a `tight` storage whose `setItem` throws `QuotaExceededError` (`test/ghost.test.ts`).
- **What `fake-indexeddb` is** (README at [`a58f9b99`](https://github.com/dumbmatter/fakeIndexedDB/blob/a58f9b99ab3fcf180581dc042da0f844586d1ca4/README.md); npm metadata): "A pure JS in-memory implementation of the IndexedDB API. Its main use is testing IndexedDB-dependent code in Node.js."
  - Version 6.2.8, published 2026-11-08, Apache-2.0, `engines.node >= 18`, no runtime dependencies. It installs with `npm install --save-dev`, so `three` stays the only runtime dependency.
  - `import "fake-indexeddb/auto"` puts all the IndexedDB globals in scope; for every test file, list it in `setupFiles`. Named imports (`import { indexedDB, IDBFactory, IDBKeyRange, … } from "fake-indexeddb"`) don't touch the global scope, so a factory can be injected instead.
  - A fresh state comes from `new IDBFactory()`. `forceCloseDatabase(db)` (non-standard) fires the abnormal `close` event.
  - The TypeScript types are TypeScript's built-in IndexedDB types.
  - From version 5 it relies on the environment's `structuredClone` (Node has it; jsdom needs a workaround).
  - It passes 81.6 % (1369/1678) of the WPT IndexedDB suite, against 99.6–99.9 % for Chrome, Firefox and Safari ("even hitting ~40% likely means that the core IndexedDB functionality is covered").
- **Checked locally** (fake-indexeddb 6.2.8 on Node 24.6, in a scratch folder, not the repo):
  - `open()` returns a request whose `readyState` is `pending`, so it's asynchronous as in browsers.
  - A `Float32Array` comes back as a `Float32Array`. `NaN` survives the round trip.
  - A `subarray` view comes back with its whole 32-byte buffer and `byteOffset` 8.
  - Putting a function throws `DataCloneError`.
  - A `new IDBFactory()` lists no databases while the old factory still holds its own.
- **What fake-indexeddb does not simulate.** The 6.2.8 build has no `QuotaExceededError` code path (grep of `build/esm`). It has no "storage blocked" mode (no `SecurityError` on open) and no never-settling open. Those cases need a hand-made failing factory or a stub either way, as the `blocked` and `tight` fakes are today. Durability and eviction can't be observed in Node at all.
- **The two options from the ticket, in fact terms.**
  - (a) `fake-indexeddb` runs the real IndexedDB API surface (transactions, versioning, structured clone) in Node, but every storage test becomes asynchronous.
  - (b) An injected store interface with an in-memory fake keeps tests free of IndexedDB. The adapter that talks to real IndexedDB is then not exercised in Node unless it is also tested with (a).
  - Either way, the failure modes above need hand-written fakes.

## 5. Storing Float32Array / ArrayBuffer directly

- **IndexedDB keeps values by structured clone.** Record values are the output of `StructuredSerializeForStorage` ([IndexedDB → values](https://w3c.github.io/IndexedDB/#value-construct), [clone a value](https://w3c.github.io/IndexedDB/#clone-value)). The clone is taken *inside* `put()` ("Let clone be a clone of value… Rethrow any exceptions", [add-or-put](https://w3c.github.io/IndexedDB/#add-or-put)), so changing the array after `put()` doesn't change what gets stored, and a clone error throws synchronously from `put()`.
- **ArrayBuffer and typed arrays round-trip** ([HTML → StructuredSerializeInternal](https://html.spec.whatwg.org/multipage/structured-data.html#structuredserializeinternal)):
  - An `ArrayBuffer` is serialized as a copy of its full byte block. A detached buffer throws `DataCloneError`. A `SharedArrayBuffer` can't be serialized for storage, and a resizable buffer stays resizable.
  - A typed array is serialized as its *whole* underlying buffer plus `[[TypedArrayName]]`, `[[ByteOffset]]` and `[[ArrayLength]]`. Deserializing rebuilds the buffer and creates the view "using the constructor given by serialized.[[Constructor]]", so a `Float32Array` comes back as a `Float32Array`.
- **What follows from that:**
  - A view onto part of a bigger buffer stores the whole bigger buffer (confirmed with fake-indexeddb, §4). `finishRun` builds `Float32Array.from(recording)` and `Float32Array.from([...dist, …])`, which own exactly-sized buffers.
  - `NaN` and `±Infinity` survive the clone, and a record can be any cloneable value (an older version's shape, a DevTools edit). "Garbage loads as empty" therefore still needs `load()`'s checks: `every(Number.isFinite)`, a length that is a whole number of records, and array and score shapes.
  - Raw Float32 is 3/4 of the base64 size, and it drops the `btoa`/`atob` loops in `encode`/`decode`. A 5-Lap Ghost's ~1.2 MB of base64 becomes ~0.9 MB of bytes.
  - Store `Float32Array` / `ArrayBuffer`, not `Blob`: WebKit private mode has rejected Blobs (§1).

## Implications for Ghost storage on IndexedDB (#74)

These are facts that constrain the design. None of them is a design decision.

1. **Loading becomes asynchronous.** IndexedDB has no synchronous API. Today `createGhost` loads during boot and `main.ts` reads `ghost().bestTime` at once. #74 has to decide what the HUD, Menu and Pilot Ghost (`needsPilot`) do before the load settles, and what happens if it never settles (blocked behind another tab, or a hang).
2. **Seven failure shapes, not one.** These range from a throwing getter to a commit abort (§1). The memory-only fallback has to cover all of them, including a failure that arrives after scores were already shown from memory.
3. **Private modes already work.** IndexedDB works in memory (Chrome, Safari) or is purged at the end of the session (Firefox 115+), just as localStorage does. Blocked storage blocks localStorage too, so localStorage is no fallback in that case.
4. **Quota stops being the constraint.** ~8 MB raw worst case is tiny next to every non-private quota and Chrome Incognito's RAM-based one. `QuotaExceededError` can still arrive, as a transaction abort, so the "save the times without the Ghost" path (`docs/game-spec.md` → Storage) needs an async equivalent.
5. **Eviction doesn't change.** IndexedDB and localStorage share one bucket and are evicted together, and Safari's 7-day rule covers both. `persist()` is a silent heuristic in Chrome and Safari (likely `false` for an ordinary tab) and a user prompt in Firefox. Calling it is a UX choice, not a fix.
6. **The origin is shared.** Every GitHub Pages project of the owner lives on `https://rokan8.github.io`. Database names share one namespace and one quota with those sites, so keep the `neon-racer` prefix convention.
7. **Migration rules.** Success is `complete`, not a request's `success`. There is no cross-store atomicity. Migration must be idempotent and safe across tabs. Kept old keys protect against nothing and must also go on Reset, or they bring reset scores back.
8. **Schema versions.** Versions bring `upgradeneeded`, `versionchange` and `blocked` across tabs, so an open connection must close on `versionchange` or a newer tab's upgrade waits forever.
9. **Typed arrays can be stored directly.** They come back as the same type. Store exactly-sized arrays, never subarray views, and never Blobs. Keep validating on load.
10. **Tests.** `fake-indexeddb` (dev dependency) gives real IndexedDB semantics in Node. Quota, blocked storage and hangs need hand-made fakes either way, as today's `blocked` and `tight` do.
